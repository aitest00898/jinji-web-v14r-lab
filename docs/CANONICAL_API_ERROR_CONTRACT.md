# Canonical API Error Contract

Status: local Web release-candidate closure, 2026-09-09

This document records the error contract between the Web client and the
canonical Worker API. It does not authorize a login retry, a business canary,
or a deployment.

## Boundary and source evidence

All Web authentication, records reads, RecordCommand writes, corrections, and
reversals use `src/canonical-api.js`. The client methods are:

```text
POST /api/web/auth/login
GET  /api/web/auth/session
POST /api/web/auth/logout
GET  /api/records
POST /api/records
POST /api/records/:id/correct
POST /api/records/:id/reverse
```

The reviewed Worker source uses one `errorResponse()` helper that emits the
flat JSON shape `{ error: string, message: string }`. The current canonical
Worker source is unchanged by this Gate and was reviewed at deployed source
SHA `18c80b5d5b645e6e2deee76b341089ee9217a154`.

The Web client also accepts the previously observed nested shape
`{ error: { code: string, message: string } }`. Both shapes are normalized at
the shared request boundary; no route has a separate persistence or error
parser.

## Normalized client error

`normalizeCanonicalApiError(payload, httpStatus)` returns exactly:

```json
{
  "code": "invalid_credentials",
  "message": "server detail retained for internal error context",
  "status": 401
}
```

Rules:

1. A flat string `error` or nested string `error.code` is accepted only when
   it matches the bounded error-code grammar.
2. A missing, non-string, empty, array, non-object, or non-JSON envelope fails
   closed to `CANONICAL_API_HTTP_<status>` (or
   `CANONICAL_API_HTTP_ERROR` when no valid numeric status exists).
3. A missing or non-string message keeps the valid code but uses the generic
   internal message `Canonical API rejected the request.`.
4. HTTP status is preserved in the error object and is never used to bypass
   authentication or scope checks.
5. The server-provided message is not rendered as UI copy. `app.js` maps known
   codes to bounded Traditional-Chinese messages and uses a safe generic
   fallback for unknown codes.

## Worker route matrix

| Operation | Endpoint | Auth boundary | Worker error envelope/status | Client handling |
| --- | --- | --- | --- | --- |
| CORS preflight | `OPTIONS /api/*` | Origin allowlist | `204`, no JSON body | No business request is sent |
| Origin rejection | Any `/api/*` with disallowed `Origin` | Before route auth | Flat `403 origin_not_allowed` | Bounded origin message |
| Login | `POST /api/web/auth/login` | Public auth endpoint | Flat `400 invalid_credentials` for malformed input; flat `401 invalid_credentials` for verifier rejection; flat `503 organization_unavailable` | Bounded login message; token remains null on rejection |
| Session probe | `GET /api/web/auth/session` | Public session probe | `200 {authenticated:false}` when absent, `200` authenticated body when valid | Invalid/missing success state does not create auth |
| Logout | `POST /api/web/auth/logout` | Requires session | Flat `401 unauthorized`; `200` on revocation | Client clears memory auth in `finally` |
| Records read | `GET /api/records` | Requires session and explicit `environment` query generated by client | Flat `401 unauthorized`; `500 internal_error` on uncaught Worker failure; `200 {records,environment}` on success | Same normalizer; no fixture fallback |
| Canonical create | `POST /api/records` | Requires session and scope | Flat `401 unauthorized`; flat `400` validator/write code; flat `403 origin_not_allowed`; flat `500 internal_error` | Same normalizer; no local write on failure |
| Canonical correction | `POST /api/records/:id/correct` | Same as create | Same shared boundary; relation mismatch is a bounded `400 CANONICAL_RELATION_TARGET_MISMATCH` candidate; validator/write codes remain source-defined | Same normalizer; append-only semantics stay server-side |
| Canonical reversal | `POST /api/records/:id/reverse` | Same as create | Same shared boundary; relation mismatch and validator/write codes use the same flat `400` contract; uncaught failure is flat `500 internal_error` | Same normalizer; no destructive client fallback |
| Unknown API route | Any unmatched `/api/*` | Origin check, then session gate where applicable | Flat `404 not_found` | Safe generic message |

The canonical records route delegates to `createRecordCommand()` and
`persistRecordCommand()` in the Worker. The four persistence destinations and
their authority rules are not changed by this contract closure.

## Safe UI mapping

The Web UI currently maps these server codes without displaying arbitrary
server text:

| Code | UI copy |
| --- | --- |
| `invalid_credentials` | `登入未通過，請確認管理密碼後再試。` |
| `organization_unavailable` | `登入服務目前無法提供組織資訊，請稍後再試。` |
| `origin_not_allowed` | `此執行來源未獲授權，沒有送出資料。` |
| `unauthorized` | `登入 session 已失效，請重新登入；沒有建立本機替代紀錄。` |
| `CANONICAL_API_AUTH_RESPONSE_INVALID` | `登入服務回傳無效 session，沒有送出資料。` |
| unknown code or HTTP fallback | Login: `登入未通過，請確認管理密碼後再試。`; business: `canonical API 拒絕了這筆資料，沒有建立本機替代紀錄。` |

Passwords, bearer tokens, Authorization headers, stack traces, SQL details,
and raw Worker messages are not rendered in the login or business-error UI.
The client uses `credentials: "omit"`; a bearer token is held only in the
current page's memory.

## Fail-closed authentication semantics

- A failed login leaves `isAuthenticated() === false` and no token in client
  state.
- A protected `401` clears the in-memory session before surfacing the error.
- A malformed or non-JSON error cannot create or retain a session.
- A successful HTTP response without `authenticated: true` and a bounded token
  is rejected as `CANONICAL_API_AUTH_RESPONSE_INVALID` and clears auth state.
- Test scope still requires an explicit authenticated UI selection; an unknown
  environment is rejected before a request is sent.
- API failure never activates local fixture or local persistence fallback.

## Regression evidence required for this closure

The local tests cover flat and nested known/unknown envelopes, missing fields,
null/non-object/non-JSON responses, HTTP status fallback for 400/401/403/404
/409/429/500, protected-401 clearing, and the shared create/correct/reverse
paths. The release candidate must additionally pass Chromium, WebKit,
security, static, integration, visual, workflow, `npm run check` where
available, and `git diff --check` before any human login retry is considered.

Human login remains a separate boundary. This Gate does not retry it.
